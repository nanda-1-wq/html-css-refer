HTML Accessibility Reference

1. What Is Web Accessibility?

Web accessibility means creating websites that everyone can use — including people with disabilities. About 15% of the world's population lives with some form of disability.

Types of Disabilities Affecting Web Use

Disability TypeExamplesCommon Assistive Tech
VisualBlindness, low vision, color blindnessScreen readers (NVDA, JAWS, VoiceOver), braille displays, magnifiers
AuditoryDeafness, hard of hearingCaptions, transcripts, visual alerts
MotorParalysis, tremors, difficulty using mouse/touchscreenKeyboard only, switch access, voice control
CognitiveAttention disorders, memory issues, learning disabilitiesClear language, consistent navigation, reduced clutter
SpeechDifficulty speakingAlternative input methods
PhotosensitiveSensitivity to flashing lights (seizures)Avoiding flashing content (<3Hz)

2. WCAG & POUR Principles

The Web Content Accessibility Guidelines (WCAG) are the international standard for web accessibility. They are organized around four principles, remembered as POUR.

P — Perceivable
Information must be presentable in ways users can perceive. If you can only convey something visually, users who can't see are excluded.

✓ Provide alt text for all meaningful images
✓ Add captions for videos and transcripts for audio
✓ Ensure sufficient color contrast (4.5:1 for normal text, 3:1 for large text)
✓ Don't use color alone to convey information
✓ Text should be resizable up to 200% without loss of functionality

O — Operable
All UI and navigation must be operable. Not all users can use a mouse.

✓ All functionality available via keyboard
✓ Visible focus indicators (don't remove outline: none without replacement)
✓ Users have enough time to read content (no auto-timeouts without warning)
✓ No content that flashes more than 3 times per second
✓ Provide skip navigation links
✓ Descriptive page titles and headings

U — Understandable
Content and operation must be understandable by users.

✓ Set the lang attribute on <html>
✓ Use clear, simple language
✓ Consistent navigation across pages
✓ Associate labels with form controls
✓ Provide error messages that explain what went wrong
✓ Use logical, hierarchical heading structure

R — Robust
Content must work with current and future assistive technologies.

✓ Use valid HTML (no duplicate IDs, proper nesting)
✓ Use semantic HTML elements where possible
✓ Use ARIA only when native HTML isn't sufficient
✓ Ensure interactive elements have accessible names

WCAG Conformance Levels

LevelMeaningTypical Use

3. Heading Structure

Proper Heading Hierarchy
Screen reader users often navigate pages using headings as a table of contents. Follow these rules:

✓ Only one <h1> per page (the main page title)
✓ Don't skip heading levels (no jumping from h2 to h4)
✓ Use headings for document structure, not for visual styling
✓ Headings should clearly describe the content that follows

<!-- Correct: logical hierarchy --> <h1>My Web Development Tutorial</h1> <h2>HTML Basics</h2> <h3>Document Structure</h3> <h3>Elements and Tags</h3> <h2>CSS Styling</h2> <h3>Selectors</h3> <h3>Box Model</h3> <!-- Wrong: skips h2, uses heading for visual style --> <h1>Page Title</h1> <h4>I just wanted smaller text...</h4> <!-- ❌ skipped h2 and h3 -->

4. Alt Text for Images

alt attribute on <img>
Screen readers read alt text aloud. Search engines use it for indexing. It also appears when images fail to load.
<!-- ✅ Good: descriptive, meaningful --> <img src="cats.jpg" alt="Two orange tabby kittens sleeping together on a gray couch"> <!-- ✅ Good: includes context/purpose --> <img src="chart.png" alt="Bar chart showing sales increased 40% from 2022 to 2024"> <!-- ✅ Functional image (link/button): describe the action --> <a href="home.html"> <img src="home-icon.png" alt="Go to Home Page"> </a> <!-- ✅ Decorative image: empty alt (screen readers skip it) --> <img src="decorative-divider.png" alt=""> <!-- ❌ Bad: too vague --> <img src="photo.jpg" alt="image"> <img src="photo.jpg" alt="photo"> <img src="photo.jpg" alt="photo of something"> <!-- ❌ Bad: redundant (don't say "image of" or "picture of") --> <img src="cat.jpg" alt="Image of a cat sitting on a mat"> <!-- ✅ Better --> <img src="cat.jpg" alt="A fluffy white cat sitting on a red mat">
⚠️ Rule of thumb: Describe what the image shows AND why it matters in context. For decorative images, use alt="" (empty string) — NOT alt="decorative" or omitting alt entirely (missing alt is an error).

5. Descriptive Link Text

Meaningful Anchor Text
Screen reader users often tab through links in isolation. Link text must make sense without surrounding context.
<!-- ✅ Good: describes destination clearly --> <a href="https://www.freecodecamp.org">Learn to code for free on freeCodeCamp</a> <a href="/privacy-policy">Read our Privacy Policy</a> <a href="resume.pdf" download>Download Jane Doe's Resume (PDF)</a> <!-- ✅ Good: image link with alt text describing destination --> <a href="/"><img src="logo.png" alt="Home — My Website"></a> <!-- ❌ Bad: vague, meaningless out of context --> <a href="https://www.freecodecamp.org">Click here</a> <a href="/privacy-policy">Read more</a> <a href="resume.pdf">Here</a> <!-- For icon-only links: use aria-label --> <a href="https://twitter.com/user" aria-label="Follow us on Twitter"> <svg aria-hidden="true">...</svg> </a>

6. Form Accessibility

Always Associate Labels with Inputs
When a screen reader focuses an input, it reads the associated label. Without a label, the user doesn't know what to enter.
<!-- ✅ Explicit association (recommended) --> <label for="user-email">Email Address:</label> <input type="email" id="user-email" name="email" required> <!-- ✅ Implicit association --> <label> Full Name: <input type="text" name="name"> </label> <!-- ✅ Fieldset + legend for radio/checkbox groups --> <fieldset> <legend>Preferred notification method:</legend> <input type="radio" id="by-email" name="notify" value="email"> <label for="by-email">Email</label> <input type="radio" id="by-sms" name="notify" value="sms"> <label for="by-sms">SMS</label> </fieldset> <!-- ✅ Error messages linked to input --> <label for="password">Password:</label> <input type="password" id="password" name="password" aria-describedby="pwd-help pwd-error" aria-invalid="true" > <p id="pwd-help">Must be at least 8 characters.</p> <p id="pwd-error" role="alert">Error: Password is too short.</p> <!-- ✅ Required field indication --> <label for="username">Username <span aria-hidden="true">*</span>:</label> <input type="text" id="username" name="username" required aria-required="true"> <p><span aria-hidden="true">*</span> Required fields</p>
Table Accessibility in Forms
When displaying form data or results in a table, always use caption, scope on th elements, and proper thead/tbody/tfoot.
<table> <caption>Employee Salary Information</caption> <thead> <tr> <th scope="col">Employee Name</th> <th scope="col">Department</th> <th scope="col">Annual Salary</th> </tr> </thead> <tbody> <tr> <td>Sarah Johnson</td> <td>Engineering</td> <td>$95,000</td> </tr> </tbody> </table>

7. Audio & Video Accessibility

Captions, Subtitles & Transcripts
Captions: Time-synced text of all audio (speech + sound effects) for deaf/HoH users.
Subtitles: Translation of speech into another language.
Transcripts: Full text version of audio/video (can be read at own pace).
<!-- Video with captions (WebVTT format) --> <video controls width="640" height="480"> <source src="tutorial.mp4" type="video/mp4"> <source src="tutorial.webm" type="video/webm"> <!-- Captions (for deaf/HoH — includes speaker labels, sound effects) --> <track kind="captions" src="captions-en.vtt" srclang="en" label="English Captions" default> <!-- Subtitles (translation) --> <track kind="subtitles" src="subtitles-es.vtt" srclang="es" label="Spanish"> <!-- Audio descriptions (describe visual content for blind users) --> <track kind="descriptions" src="descriptions-en.vtt" srclang="en" label="Audio Descriptions"> Your browser doesn't support the video element. </video> <!-- Transcript below the video --> <details> <summary>Video Transcript</summary> <p>[Transcript text here...]</p> </details>

WebVTT Caption File Format

<!-- captions-en.vtt --> WEBVTT 00:00:01.000 --> 00:00:04.000 Hello and welcome to this tutorial. 00:00:05.000 --> 00:00:09.000 Today we'll learn about HTML accessibility. 00:00:10.000 --> 00:00:14.000 [keyboard typing sounds] Let's start by looking at the code.

8. Keyboard Navigation

tabindex
Controls whether and how an element participates in keyboard (Tab key) navigation.
tabindex="0"
Makes element focusable in its natural document order. Use to make non-interactive elements (div, span) keyboard-accessible.
tabindex="-1"
Removes element from tab order, but allows JavaScript to focus it programmatically with .focus().
tabindex="1+" (AVOID)
Positive values override natural tab order. Creates confusing navigation. Never use values greater than 0.
<!-- Naturally focusable (no tabindex needed): --> <!-- a, button, input, select, textarea, details --> <!-- Make a div keyboard focusable --> <div tabindex="0" role="button" onclick="doSomething()">Click Me</div> <!-- Remove from tab order (accessible only via JS) --> <div id="modal" tabindex="-1">Modal content</div> <script> document.getElementById("modal").focus(); // Works! </script> <!-- Skip button: focusable with tabindex="0" --> <a href="#main-content" tabindex="0">Skip to main content</a> <!-- ❌ Never use positive tabindex --> <button tabindex="3">This breaks tab order</button>
⚠️ The default Tab order follows document order. Design your HTML so the natural reading order matches the logical flow of the page.
accesskey
Defines a keyboard shortcut to activate or focus an element. The shortcut is the specified key combined with a modifier key that varies by OS and browser.
accesskey="letter"
Single character shortcut. Activation: Alt+key (Windows/Linux), Control+Option+key (Mac).
<button type="submit" accesskey="s">Save (Alt+S / Ctrl+Opt+S)</button> <button type="reset" accesskey="c">Cancel (Alt+C)</button> <a href="/home" accesskey="h">Home (Alt+H)</a> <!-- Always document the shortcuts visibly for users! --> <p>Keyboard shortcuts: <kbd>Alt+S</kbd> to save, <kbd>Alt+C</kbd> to cancel.</p>
⚠️ Use sparingly. Accesskeys can conflict with browser or OS shortcuts. Document them prominently. Don't rely on them as the only way to perform actions.

Skip Navigation Links

Skip to Main Content
A link at the top of the page (often visually hidden until focused) that allows keyboard users to jump past repetitive navigation to the main content. Critical for pages with long navbars.
<!-- First element in <body> --> <a href="#main-content" class="skip-link">Skip to main content</a> <header> <nav>...many navigation links...</nav> </header> <main id="main-content"> <!-- Tab goes here when skip link is used --> <h1>Page Title</h1> ... </main> <!-- CSS: hidden until focused --> <style> .skip-link { position: absolute; top: -100px; left: 0; background: #000; color: #fff; padding: 10px 20px; z-index: 999; font-size: 1.1em; } .skip-link:focus { top: 0; } </style>

9. ARIA Attributes

ARIA (Accessible Rich Internet Applications) attributes add accessibility information that HTML alone can't provide. The first rule of ARIA: use native HTML elements instead whenever possible.

aria-label
Provides an accessible name for an element that has no visible text label. The value is announced by screen readers instead of any visual content.
<!-- Icon-only button --> <button aria-label="Search the website"> 🔍 </button> <!-- Icon-only nav link --> <a href="https://twitter.com/user" aria-label="Follow us on Twitter"> <svg aria-hidden="true" focusable="false">...twitter icon...</svg> </a> <!-- Distinguish multiple navs --> <nav aria-label="Main navigation">...</nav> <nav aria-label="Breadcrumb">...</nav> <nav aria-label="Footer links">...</nav>
aria-labelledby
Associates an element with visible text elsewhere on the page (by ID). The referenced element's text becomes the accessible name. More robust than aria-label because it reuses existing visible text.
<!-- Input labeled by existing text --> <label id="search-label">Search Products:</label> <input type="text" aria-labelledby="search-label"> <!-- Modal labeled by its title --> <div role="dialog" aria-labelledby="dialog-title" aria-modal="true"> <h2 id="dialog-title">Confirm Deletion</h2> <p>Are you sure you want to delete this item?</p> </div> <!-- Multiple IDs: combine labels --> <h2 id="billing">Billing</h2> <p id="billing-desc">Enter your billing address:</p> <input type="text" aria-labelledby="billing billing-desc">
aria-describedby
Links an element to additional descriptive text (by ID). The description is read after the element's label. Use for instructions, hints, error messages, or additional context.
<!-- Password with requirements --> <label for="password">Password:</label> <input type="password" id="password" name="password" aria-describedby="pwd-requirements"> <p id="pwd-requirements"> Must be 8+ characters, include a number and special character. </p> <!-- Input with hint AND error --> <label for="username">Username:</label> <input type="text" id="username" aria-describedby="username-hint username-error"> <p id="username-hint">Letters and numbers only, 3–20 characters.</p> <p id="username-error" role="alert">Error: Username is already taken.</p>
aria-hidden
When "true", removes an element from the accessibility tree — screen readers skip it completely. Use for decorative icons, emojis, and visually redundant content.
<!-- Decorative icon + visible text --> <button> <span aria-hidden="true">⚙️</span> Settings </button> <!-- Screen reader announces: "Settings, button" (not "gear emoji Settings button") --> <!-- Decorative image alternative: use empty alt on <img> instead --> <img src="decorative-wave.svg" alt=""> <!-- Hide duplicated text --> <span aria-hidden="true">★★★★☆</span> <span class="sr-only">4 out of 5 stars</span>
aria-live
Marks a region as a "live region" — screen readers automatically announce content changes without user action. Essential for dynamic content (notifications, search results, chat).
"off"
Default. Changes are not announced.
"polite"
Announced when the user is idle. Non-urgent updates (search results, status messages).
"assertive"
Announced immediately, interrupting current speech. Use sparingly for urgent errors only.
<!-- Status messages (non-urgent) --> <div aria-live="polite" aria-atomic="true"> <!-- JS updates this text; screen reader reads the change --> Showing 5 of 20 results. </div> <!-- Error/alert messages (urgent) --> <div aria-live="assertive" role="alert"> Error: Your session has expired. Please log in again. </div> <!-- Better: use role="status" for polite, role="alert" for assertive --> <div role="status">Form saved successfully.</div> <div role="alert">Error: Invalid credit card number.</div>
aria-expanded, aria-checked, aria-selected
Communicate interactive state to screen readers.
<!-- Expand/collapse button --> <button aria-expanded="false" aria-controls="menu" onclick="toggleMenu()"> Menu </button> <ul id="menu" hidden> <li><a href="/">Home</a></li> </ul> <!-- Custom checkbox --> <div role="checkbox" aria-checked="false" tabindex="0"> Subscribe to newsletter </div> <!-- Tab panel --> <button role="tab" aria-selected="true" aria-controls="panel1">Tab 1</button> <button role="tab" aria-selected="false" aria-controls="panel2">Tab 2</button>
aria-required, aria-invalid, aria-disabled
Communicate form validation states to assistive technologies.
<!-- Required field --> <input type="text" aria-required="true" required> <!-- Invalid input with error message --> <input type="email" id="email" aria-invalid="true" aria-describedby="email-error"> <p id="email-error" role="alert">Please enter a valid email address.</p> <!-- Disabled element (prefer HTML disabled attribute instead) --> <button aria-disabled="true">Cannot click yet</button>
aria-current
Indicates the current item within a set — current page in navigation, current step in a wizard, current date in a calendar.
<!-- Current page in navigation --> <nav> <ul> <li><a href="/">Home</a></li> <li><a href="/about" aria-current="page">About</a></li> <li><a href="/contact">Contact</a></li> </ul> </nav> <!-- Other values: "step", "date", "time", "location", "true" -->

The role attribute tells assistive technologies what an element IS. Prefer native semantic HTML elements. Only use roles when HTML alone doesn't describe the element's purpose.

11. Language Attribute

lang attribute
Tells screen readers what language to use for pronunciation. Also affects browser spell-check and translation tools. Required on <html> for accessibility compliance.
<!-- Set page language --> <html lang="en"> <!-- English --> <html lang="ar"> <!-- Arabic --> <html lang="fr"> <!-- French --> <html lang="zh"> <!-- Chinese --> <html lang="es"> <!-- Spanish --> <html lang="de"> <!-- German --> <!-- Set language of a specific phrase (different from page language) --> <p> There is a certain <i lang="fr">je ne sais quoi</i> about this. </p> <!-- Language codes: ISO 639-1 (2 letters) or ISO 639-1 + region --> <html lang="en-US"> <!-- American English --> <html lang="en-GB"> <!-- British English --> <html lang="zh-CN"> <!-- Simplified Chinese --> <html lang="pt-BR"> <!-- Brazilian Portuguese -->

12. Focus Management & Visible Focus

Visible Focus Indicators
Keyboard users need to see which element is focused. Never remove focus outlines without replacing them with a better alternative.
<!-- ❌ Never do this --> <style> * { outline: none; } /* removes all focus indicators */ button:focus { outline: 0; } /* removes focus on buttons */ </style> <!-- ✅ Custom focus style that's more visible --> <style> :focus { outline: 3px solid #3498db; outline-offset: 2px; } /* Or using focus-visible (only shows for keyboard, not mouse) */ :focus-visible { outline: 3px solid #3498db; outline-offset: 2px; border-radius: 3px; } </style>
Focus Trapping in Modals
When a modal dialog opens, Tab should cycle through modal elements only — not go to the background page. Focus should return to the trigger element when the modal closes.
<!-- When modal opens: --> <!-- 1. Move focus to first focusable element in modal --> <!-- 2. Trap Tab/Shift+Tab within modal --> <!-- 3. Close on Escape key --> <!-- 4. Return focus to the element that opened the modal --> <button id="open-modal">Open Modal</button> <div role="dialog" aria-labelledby="modal-title" aria-modal="true" id="modal" tabindex="-1"> <h2 id="modal-title">Confirm Action</h2> <p>Are you sure?</p> <button id="confirm">Confirm</button> <button id="close-modal">Cancel</button> </div>

13. Color Contrast

Color Contrast Ratios (WCAG AA)
Sufficient contrast ensures text is readable for users with low vision or color blindness.
Text TypeMinimum Ratio (AA)Enhanced Ratio (AAA)
Normal text (under 18pt / 14pt bold)4.5:17:1
Large text (18pt+ / 14pt+ bold)3:14.5:1
UI components (buttons, inputs, focus outlines)3:1—
Decorative text / inactive componentsNo requirement—
<!-- ✅ Good contrast examples: --> <!-- Black (#000000) on white (#ffffff): ratio 21:1 ✅ --> <!-- Dark blue (#2c3e50) on white (#ffffff): ratio ~8:1 ✅ --> <!-- White (#ffffff) on blue (#3498db): ratio ~3.6:1 ✅ (large text) --> <!-- ❌ Poor contrast examples: --> <!-- Light gray (#aaaaaa) on white (#ffffff): ratio ~2.3:1 ❌ --> <!-- Yellow (#ffff00) on white: ratio 1.07:1 ❌ -->
🛠️ Free contrast checking tools:
• WebAIM Contrast Checker — webaim.org/resources/contrastchecker
• Colour Contrast Analyser — desktop app
• Chrome DevTools — Accessibility panel shows contrast ratios
Never Use Color Alone
About 8% of men and 0.5% of women have color blindness. Don't use color as the only way to convey information.
<!-- ❌ Color only: colorblind users can't tell which fields are required --> <style> .required { color: red; } /* only way to distinguish required */ </style> <input class="required" type="text" name="name"> <!-- ✅ Color + icon + text --> <label for="name"> Name <span aria-hidden="true">*</span>: </label> <input type="text" id="name" name="name" required aria-required="true"> <p><span aria-hidden="true">*</span> Required fields</p> <!-- ✅ Error: color + icon + text (not just red border) --> <input type="email" id="email" aria-invalid="true" aria-describedby="email-err"> <p id="email-err" style="color: red;"> ❌ Please enter a valid email address. </p>

14. Accessibility Checklist

HTML Structure

✅ <html lang="..."> is set correctly
✅ One <h1> per page, headings in logical order (no skipped levels)
✅ <main> wraps the primary content
✅ <nav> used for navigation with aria-label to distinguish multiple navs
✅ Skip-to-main-content link is the first focusable element
✅ Page title (<title>) is descriptive and unique

Images & Media

✅ All meaningful images have descriptive alt text
✅ Decorative images have empty alt text (alt="")
✅ Videos have captions (not just subtitles)
✅ Audio has a transcript
✅ <iframe> has a title attribute

Forms

✅ Every input has an associated <label>
✅ Radio/checkbox groups use <fieldset> + <legend>
✅ Error messages are linked with aria-describedby
✅ Required fields are indicated (not just with color)
✅ Button types are explicitly set (type="submit", etc.)

Tables

✅ Table has a <caption>
✅ Column headers use <th scope="col">
✅ Row headers use <th scope="row">
✅ Complex tables use id + headers attributes

Keyboard & Interaction

✅ All interactive elements are keyboard accessible
✅ Focus indicators are visible (not just :focus { outline: none })
✅ Tab order follows logical reading order
✅ No keyboard traps (except intentional modal trapping)
✅ Modals: focus trapped inside, Escape closes, focus returns

Color & Contrast

✅ Text contrast ratio ≥ 4.5:1 (normal) or ≥ 3:1 (large)
✅ UI components contrast ratio ≥ 3:1
✅ Color is not the only way information is conveyed
✅ Links are distinguishable from surrounding text (not just by color)
